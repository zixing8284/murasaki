`useDraggable`/`useResizable` now drive drags and resizes with two input paths and are transform-aware. Windows can be dragged and resized with mouse, pen and touch (including Chrome DevTools device emulation), and interaction stays correct when an ancestor applies a CSS `transform` such as a scaled or rotated desktop canvas — pointer deltas are converted into the target's local space via the ancestor transform. The window title bar and resize grip are marked `touch-action: none` so touch gestures aren't stolen for scrolling, and the title bar is a taller, easier-to-hit drag target on coarse (touch) pointers.

Touch is handled with **native touch events** (`touchstart`/`touchmove`/`touchend`) instead of pointer events, and the drag listener lives on the window **frame** (not the title bar) while the title bar acts as a coordinate **handle region**. This fixes the case where the touch circle dips just below the title bar: Chrome's touch-adjustment snaps the event target onto the menubar/content sibling below the title bar (whose events bubble through the frame, not the title bar), so a title-bar listener would miss them. By listening on the frame and deciding by the touch **coordinates** (which are never adjusted) via a point hit-test, a press whose centre is on the title bar starts a drag even when its target was snapped below — while a press whose centre is actually on the menubar does not, so menus and content scrolling keep working. Touch events implicitly capture to the start target, so moves keep flowing across other windows' iframes without pointer capture. The mouse/pen path keeps using Pointer Events with `setPointerCapture`. `WindowTitleBar` also maximizes on a touch double-tap (touch never fires `dblclick`), matching the mouse double-click behavior.
